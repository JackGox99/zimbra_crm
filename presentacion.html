Caso de estudio: Zimbra

El negocio que se está modelando

Zimbra es una empresa de software cuya plataforma estrella — Zimbra Collaboration Suite (ZCS) — provee correo, calendario y colaboración a miles de empresas. Su modelo comercial:

📣 Campaña → 👤 Prospecto → 📊 Interacciones (scoring) → ✅ Calificado → 📋 Propuesta → 💰 Venta → 🤝 Cliente

Procesos clave identificados

  • Gestión de campañas de marketing.
  • Captura y scoring de prospectos.
  • Trial gratuito de 60 días.
  • Propuestas comerciales y cierre de ventas.
  • Sincronización con Salesforce.

Decisión de diseño

Implementamos el flujo end-to-end como un CRM transaccional real para que cada propiedad ACID, trigger, SP y UDF se vea en un escenario de negocio concreto — no como demos artificiales.

ENTREGA 1

Historias de usuario

Ejemplos representativos con criterios de aceptación

HU-01 · Calificación automática

"Como gerente comercial quiero que un prospecto se promueva automáticamente cuando su scoring supere 15 puntos, para no perder leads calientes."

Criterios: Al registrar una interacción, la BD actualiza la puntuación y promueve a Calificado en la misma transacción si cruza el umbral.

Responsable: Hayder Barrera

HU-02 · Cierre transaccional de venta

"Como ejecutivo de ventas quiero que aceptar la propuesta cree cliente y venta a la vez, sin estados intermedios."

Criterios: El endpoint cerrar-venta ejecuta 4 operaciones en una transacción con SAVEPOINTs. Si falla cualquiera, todo se revierte.

Responsable: Julian Artunduaga

HU-03 · Bitácora de cambios

"Como auditor quiero que cada cambio de estado de prospecto quede registrado automáticamente."

Criterios: El trigger trg_audit_estado_prospecto inserta una fila en REPORTE (tipo Auditoria Estado Prospecto, JSON en resultado) cada vez que el estado cambia.

Responsable: Valery Pamplona

HU-04 · Extensión de trial

"Como comercial quiero extender el trial de un prospecto prometedor para darle más tiempo de evaluación."

Criterios: El SP sp_extender_trial valida que tenga trial activo y que los días estén entre 1 y 90.

Responsable: Equipo completo

Ejemplo de DDL — tabla VENTA

CREATE TABLE VENTA (
    id_venta       INT AUTO_INCREMENT PRIMARY KEY,
    fecha_venta    DATE NOT NULL,
    monto          DECIMAL(12,2) NOT NULL,
    estado         VARCHAR(30) NOT NULL,
    metodo_pago    VARCHAR(40),
    id_propuesta   INT NOT NULL UNIQUE,    -- una propuesta = una venta
    id_cliente     INT NOT NULL,
    FOREIGN KEY (id_propuesta) REFERENCES PROPUESTA(id_propuesta),
    FOREIGN KEY (id_cliente)   REFERENCES CLIENTE(id_cliente),
    CHECK (monto > 0)                       -- regla de negocio
);

Caso estrella: cerrar venta con 3 SAVEPOINTs

Endpoint POST /api/ventas/cerrar-venta

BEGIN
  ├─ Carga propuesta + validaciones de negocio
  ├─ SAVEPOINT sp1
  │     UPDATE PROPUESTA SET estado = 'Aceptada'
  ├─ RELEASE sp1
  ├─ SAVEPOINT sp2
  │     INSERT INTO CLIENTE (...)
  │     ┌─ si UNIQUE conflict (cliente ya existe — recompra):
  │     │     ROLLBACK TO sp2
  │     │     SELECT cliente existente
  │     └─ sino: RELEASE sp2
  ├─ SAVEPOINT sp3
  │     UPDATE PROSPECTO SET estado = 'Convertido'
  │     INSERT INTO VENTA (...)
  ├─ RELEASE sp3
COMMIT
Resultado: si cualquier paso falla irrecuperablemente, la transacción completa se revierte y nada queda persistido. Si solo falla la creación del cliente, se recupera el existente con ROLLBACK TO sp2 y la venta continúa.

ENTREGA 2

Backend conectado

FastAPI + SQLAlchemy 2.0 + MySQL 8

9 modelos ORM

Sintaxis SQLAlchemy 2.0 con Mapped[] y relaciones tipadas. Mapean directamente a las tablas SQL.

Routers REST

Un router por entidad bajo /api/*. Cada uno expone GET, POST, PUT, DELETE.

Servicios transaccionales

scoring_service y venta_service encapsulan transacciones explícitas con with db.begin(): y with db.begin_nested(): para los SAVEPOINTs.

Endpoints transaccionales clave

  • POST /api/ventas/cerrar-venta — cierre con 3 SAVEPOINTs.
  • POST /api/interacciones/registrar — INSERT + recálculo de scoring.
  • POST /api/prospectos/{id}/marcar-inadecuado — descalificación atómica.

Configuración ACID del motor

  • InnoDB · REPEATABLE READ (default).
  • autocommit=False + with db.begin(): explícito.
  • innodb_flush_log_at_trx_commit=1 — durabilidad en disco.

ENTREGA 3

Triggers

4 triggers integrados al flujo de negocio

TriggerEventoRegla de negocio
trg_interaccion_actualiza_scoring AFTER INSERT en INTERACCION_MARKETING Suma el peso al scoring y promueve a Calificado si supera 15.
trg_propuesta_aceptada_promueve_prospecto AFTER UPDATE en PROPUESTA Si la propuesta pasa a Aceptada, marca al prospecto como Convertido.
trg_prospecto_inadecuado_resetea_score BEFORE UPDATE en PROSPECTO Si pasa a Inadecuado, fuerza puntuacion = 0.
trg_audit_estado_prospecto AFTER UPDATE en PROSPECTO Inserta una fila en REPORTE (tipo Auditoria Estado Prospecto) con el cambio en JSON.
Diseño: los triggers centralizan reglas que antes vivían en Python. Ahora ejecutarse desde Swagger, SQL manual o el backend produce el mismo resultado — la BD garantiza la regla.

Procedimientos almacenados

3 SPs con sentido de negocio

sp_reporte_mensual_ventas

Entrada: año, mes.

Salida: total facturado, # ventas, top campaña.

Persiste el reporte en REPORTE automáticamente.

Caso: cierre comercial mensual.

sp_extender_trial

Entrada: id_prospecto, días (1-90).

Valida que tenga trial activo y suma los días.

Caso: dar más tiempo a un lead prometedor.

sp_marcar_trials_vencidos

Recorre prospectos con trial vencido que no convirtieron y los pasa a Inadecuado.

Encadena 3 triggers al ejecutarse.

Caso: limpieza periódica del pipeline.

Endpoints en el backend

POST /api/automatizacion/reporte-mensual
POST /api/automatizacion/extender-trial/{id}?dias=N
POST /api/automatizacion/limpiar-trials-vencidos
